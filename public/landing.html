Version control for CRM agents

Agents never write to your CRM. They open PRs against it.

Git CRM is a git-style layer in front of Attio and HubSpot. Every AI agent works on its own branch and opens a pull request with evidence. Git CRM three-way-merges them, catches conflicts between agents, holds risky changes for a human, and lets you revert anything.

The problem

Every CRM agent today is last-write-wins.

Call-notes agents, enrichment tools, AI SDRs, inbox agents and cleanup bots all write to the same records, at the same time, with no review and no undo.

Silent overwrites

The enrichment tool overwrites a title a rep corrected an hour ago. Nobody notices.

Forecast drift

An agent bumps a deal from $20k to $45k and the board forecast moves with nobody signing off.

Bad merges

A dedup bot merges two different people named "Alex Chen". Unpicking it is miserable.

Stale approvals

"Move Acme to Negotiation" was right at 9am. It gets approved at 4pm, after Acme emailed to say they're pausing.

How it works

The workflow your engineers already trust, for customer data.

Git CRM is a layer, not a new CRM. Reps keep working in HubSpot or Attio. Agents keep calling what looks like their CRM's API.

01

Agents branch

Each agent reads main and writes only to its own branch, e.g. agent/inbox/2. It can't touch the source of truth.

02

They open a PR

Every changed field cites the email, web page or call that justifies it, with a verbatim quote.

03

Git CRM checks it

Three-way merge against main, conflict detection, branch-protection policy, agent trust, and a staleness re-check when new evidence lands.

04

Merge, then sync

Safe changes auto-merge; risky ones wait for a human. Merged changes are written back to your CRM. Every merge, including auto-merges, can be reverted.

emails · web pages · calls → agents → branch + PR → merge engine (conflicts · policy · trust · staleness) → human review → main (event log) → Attio / HubSpot
Branches & pull requests

Every agent change is a PR with receipts.

Agents propose; they never commit. Each PR shows the field-level diff, the policy that applies, and the evidence behind every value.

  • One branch per agent run (agent/inbox/2, agent/hygiene/1 …)
  • Verbatim quotes from the email, page or call that justify each field
  • Schema changes are PRs too: add deal.procurementContact and backfill 4 deals in one reviewable change
Three-way merge & conflicts

When two agents disagree, you see it like a merge conflict.

base = main when the branch forked, ours = main now, theirs = the branch. Field-level conflicts surface instead of the last writer silently winning.

  • Conflict kinds: field, deleted, merged-away and schema
  • Semantic rebase: an edit to a contact that was since merged as a duplicate is moved onto the surviving record automatically
  • Pick a side or enter a value; the resolution is recorded with the merge

Stale-decision detection

PRs re-check themselves when the world changes.

An approval queue judges a proposal once. Git CRM re-checks every open PR when new evidence lands. "Move Acme to Negotiation" flips to stale the moment Priya's "we're pausing until Q1" email arrives.

  • Read-set version checks: if a field the agent read has changed, the PR is re-inspected
  • An evidence judge (deterministic, or Claude when a key is set) catches contradictions
  • A contradiction blocks the normal merge button
Branch protection & agent trust

Enrichment flows. Revenue waits for a human.

Policy tiers per field and per operation decide what auto-merges, what needs review and what is blocked. Agents earn trust from their track record, but some things always need a person.

  • Every agent has a record: merged, reverted, went stale
  • Probation → trusted → autonomous as the record improves
  • Money, pipeline stage, identity merges and schema always need a human

Triage at agent scale

Fifty PRs a day? You only see the ones that need you.

Most agent changes are low risk and merge themselves. The rest are sorted automatically by what they touch, so you review a category at a time instead of a wall of PRs.

  • Every PR is categorized from its diff (money & stage, merges & deletes, schema, deal updates, new records, data cleanup, enrichment)
  • A "Needs you" filter: only PRs held by policy, gone stale, or in conflict
  • Group by category or by agent, then approve a whole group in one click
  • Bulk approve skips anything stale, conflicting or blocked. Record merges and schema changes are always one at a time

Revert · time travel · blame

Nothing is ever overwritten. Anything can be undone.

Every change is an immutable event with its actor, reason and evidence. The CRM is a fold of the log, so any past state is one replay away, and you can go back to it.

  • Revert any merged PR, auto-merged ones included, by writing inverse events. A reverted agent drops back to probation
  • Restore the whole CRM to any moment: drag the slider back, click "Restore to this point". Everything since is undone as one PR, and reverting that PR undoes the restore
  • Drag a slider to see deals and the forecast as they were on any date
  • Per-field blame: who changed it, when, why, and on what evidence
Chrome side panel

Review agent changes on the record itself.

Open any deal, contact or company in HubSpot or Attio and the Git CRM side panel shows that record's pending agent PRs: diff, evidence, policy and staleness, with Approve & merge or Reject.

  • Per-field history for the record you're looking at
  • Reads only the tab URL, never the page
  • Salesforce and Pipedrive record pages are recognised too

Drop-in API proxy

Your existing agents don't change. Swap one base URL.

Point an agent at Git CRM's HubSpot- or Attio-compatible proxy and every write becomes a reviewable PR. The agent gets a 202 back with the PR it opened and why it's held.

  • HubSpot CRM v3: /api/proxy/hubspot/…
  • Attio v2: /api/proxy/attio/v2/objects/{object}/records/{id}
  • Tag the caller with x-mainline-agent for per-agent trust
bash
curl -X PATCH https://gitcrm-production.up.railway.app/api/proxy/hubspot/crm/v3/objects/deals/acme-platform \
  -H 'content-type: application/json' -H 'x-mainline-agent: sdr-bot' \
  -d '{"properties":{"amount":"45000","dealstage":"contractsent"}}'
# → 202 {"mainline":{"status":"pending_review","pr":"pr_1","tier":"review","reasons":["deal.amount $20,000 → $45,000 (+$25,000) exceeds $10k threshold", …]}}
The agents

Four reference agents. Or bring your own.

Git CRM ships with four agents so you can see the whole loop. Each works with no API key using deterministic rules; with an Anthropic key, Claude fills in what the rules miss. None of them can write to the CRM: they can only open PRs.

Inbox agent

Reads email threads and keeps contacts, deals and stages current, quoting the email as evidence.

Opens: Acme, Discovery → Negotiation, $20k → $45k

Hygiene agent

Finds duplicate contacts and normalizes names, titles and phone numbers.

Opens: merge "Priya S." into "Priya Sharma"

Schema agent

Notices information the CRM has no field for and proposes the field, with a backfill.

Opens: add deal.procurementContact, fill 4 deals

Web watcher

Watches account websites (careers, pricing, about) and turns changes into signals. Scrapes real sites via Firecrawl.

Opens: Northwind headcount 180 → 220 (auto-merges)

Already have agents? Point them at the Attio- or HubSpot-compatible proxy and name them with one header. Every write they make becomes a PR with the same policy, trust, conflict and revert rules.

Connect your Attio or HubSpot

Self-host one copy per workspace. Your team keeps working in their CRM as usual.

  1. Deploy your own copyRailway works out of the box (railway.json is included), or any Node host: npm run build && npm start.
  2. Create a CRM token and set it on the serverAttio: an access token with records read-write and object configuration read → ATTIO_TOKEN. HubSpot: a private app with companies, contacts and deals read + write → HUBSPOT_TOKEN.
  3. Settings → Integrations → Import nowPulls your companies, people and deals into main, then syncs edits from your CRM every 20 seconds.
  4. Install the Chrome extensionLoad it unpacked, then set "Git CRM server" to your URL. Pending PRs appear next to the record in Attio or HubSpot.
  5. Route your agents through the proxySwap their base URL for https://your-host/api/proxy/attio/v2/… (or /hubspot/…) and add an x-mainline-agent header.

Once it's connected

  • Your team edits in Attio or HubSpot as normal. Their edits sync onto main within ~20 seconds. That's what makes conflicts and staleness real.
  • Agents get a 202 and a PR number instead of writing. Low-risk changes auto-merge; money, stage, dedups and schema wait for a person.
  • Approve in Git CRM or on the record itself via the side panel. Approved changes are written back to your CRM.
  • Undo anything: revert a PR, or restore the whole CRM to a moment. Both write back to your CRM too.

What's not there yet

  • One workspace per deployment, no login. The CRM token is a server setting, and anyone with your URL can merge. "Connect Attio" OAuth and accounts are next.
  • Only agents you route through the proxy are governed. An agent holding its own CRM token can still bypass Git CRM.
  • The proxy covers companies, people and deals on core fields (name, domain, headcount, industry, email, title, phone, amount, stage). Notes, tasks, lists and custom attributes pass by.
  • The inbox agent reads the demo emails; there's no Gmail connection yet. Human edits made directly in your CRM aren't PRs, but restore-to-a-point covers them.
Why not just an approval queue?

Queues work for one agent. They break with many.

An approve-this-diff queue shows one proposal at a time against live data. Once several agents work concurrently, you need what version control already solved.
